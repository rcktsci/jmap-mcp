# Бриф: фаза 3 — скрипт живой проверки Stalwart (tools/live_check.py)

Дата: 2026-10-27. Роль: **разработчик**. Репо: `rcktsci/jmap-mcp`, корень = рабочий каталог.

## Зачем

Все 15 тулов реализованы и покрыты мок-тестами (139 тестов). Но JMAP-специфика Stalwart отличается
от RFC в деталях, которые ломают реализацию тихо. Список из 16 пунктов уже зафиксирован в
`docs/tools-schema.md` §1.7 (и продублирован в `reviews/schema-review.md`, таблица рисков).
Нужен **исполняемый зонд**, который проверяет эти пункты на живом сервере и печатает вердикт по
каждому: что работает, что не поддерживается, что сломалось. Ключ и адрес подаются через
окружение — в скрипте никаких секретов.

## Что сделать

Один файл `tools/live_check.py` (+ тест на мок-сервере, если уместно) — **не** менять код тулов.

### Вход

- `STALWART_URL` — базовый URL живого Stalwart (например `https://mail.example.com`).
- `STALWART_API_KEY` — API key аккаунта (`API_…`).
- `STALWART_SESSION_PATH` — необязательно, по умолчанию `/jmap/session`.
- Ключ **не** печатается, **не** логируется; в выводе — только `sha256(key)[:8]`.

### Что проверять (16 пунктов §1.7)

1. `GET {base}/jmap/session` отдаёт 200 с `apiUrl`, `primaryAccounts["urn:ietf:params:jmap:mail"]`,
   `capabilities` (core/mail/submission?), `downloadUrl`, `uploadUrl`.
2. `Thread/get` — поддерживается ли; какие поля отдаёт (`name`? `emailIds`? `totalEmails`?).
3. `Email/query` + `calculateTotal: true` — работает ли и что стоит (время ответа).
4. Полнотекстовый оператор (`text` в фильтре) — работает ли без индекса.
5. Фильтры `header`, `before`, `after`, `hasKeyword`, `notKeyword` — каждый отдельно.
6. Точные строки `role` у `Mailbox/get` (inbox/drafts/sent/trash/junk/archive/other).
7. `downloadUrl`/`uploadUrl`: реальный формат шаблона, нужна ли авторизация, имя multipart-поля.
8. `EmailSubmission/set` + `onSuccessUpdateEmail` — поддерживается ли перенос Drafts→Sent.
9. `Identity/get`: поля `replyTo`, `isDefault` присутствуют ли.
10. `textBody` vs `bodyValues` — что приходит при запросе тела.
11. Набор keywords (`$seen`, `$flagged`, `$draft`, `$answered`) — какие принимает `Email/set`.
12. `state` в ответах — есть ли account state (и в session, и в `Email/changes`).
13. `$answered` в `Email/set` — принимается ли.
14. `totalEmails`/`unreadEmails` у `Mailbox/get` — есть ли без явного запроса свойств.
15. `Email/query` с `limit: 0` — принимает ли сервер.
16. `uploadUrl` — принимает ли `POST` с multipart и Bearer.

### Формат вывода

- Таблица: `№ | проверка | вердикт | доказательство`.
  Вердикт строго: `ok` / `unsupported` / `error` / `skipped`.
  «Доказательство» — короткая выдержка (ключ/значение/первые 200 символов ответа), **без bearer**.
- Итог: сколько `ok` / `unsupported` / `error`.
- Ненулевой код возврата, если есть `error` (чтобы CI/скрипт это видели).
- Никаких файлов не писать (кроме явного `--json <path>` по флагу).

### Требования

- Асинхронный `httpx`, тот же стиль, что в `src/mcp/jmap.py` (можно переиспользовать `JmapClient`:
  он уже умеет session/call/проверку апстрима/кэш).
- Каждая проверка — отдельная функция, устойчивость к исключениям: одна проверка не должна ронять
  остальные (ошибка → вердикт `error` + текст).
- Таймауты из конфига, `limit: 1` в запросах, чтобы не тянуть лишнего.
- Никаких изменений в `src/` — только новый файл `tools/live_check.py` (+ свой тест, если нужен).

## Гейты приёмки

1. `python tools/live_check.py` без `STALWART_URL` → понятная ошибка «нужен STALWART_URL», код возврата ≠ 0.
2. Покрытие всех 16 пунктов: каждая проверка присутствует и печатает строку таблицы.
3. Ни в одном месте вывода нет значения bearer.
4. `python -m pytest -q` — зелёное (существующие тесты не сломаны).
5. `git status --porcelain -uall` — только `tools/live_check.py` (+ тест, если добавлен). Ничего не закоммичено.

## Границы

- Не коммитить и не пушить.
