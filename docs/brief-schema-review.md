# Бриф: ревью схем инструментов jmap-mcp

Дата: 2026-10-27. Роль: **ревьюер** (не автор). Проект: `rcktsci/jmap-mcp`.

## Что это

MCP-сервер — **stateless credential-transparent proxy** «MCP → JMAP»: клиент (opencode) шлёт
`Authorization: Bearer <Stalwart API Key>`, сервер проксирует этот заголовок в JMAP-вызовы к
Stalwart и ничего не хранит. Стек: Python 3.14 + `mcp` SDK 2.x (`MCPServer`). Без БД, без UI, без
health. 15 инструментов.

## Что проверять

1. **Внутренняя согласованность.** out-схема тула ↔ ключи out в `tools-schema.md` ↔ сигнатуры в
   `tools_schema.py`. Нет полей-призраков, нет читаемых полей без схемы, нет расхождений между
   JSON-блоками в .md и сгенерированными (скрипт это уже сверяет — проверь, что сверка реально
   проходит, запустив скрипт).
2. **Качество для агента.** Читает ли агент описание тула и понимает семантику без чтения кода?
   Есть ли пагинация (`position`/`has_more`), счётчики, форматы дат, единицы размера? Есть ли
   двусмысленные имена — например `state` в `whoami` = токен аккаунта, а в `list_changes` = state-токен
   JMAP; одно и то же слово — разные вещи.
3. **Валидность.** Все 30 схем прошли `check_schema`? Нет ли схем, формально валидных, но
   бессмысленных (пустые `properties`, `anyOf` без различения, `required` с полями, которых нет в
   выдаче).
4. **Выразимость ограничений.** Pydantic не выражает `additionalProperties: false` в input-схеме,
   XOR (`mailboxRole` vs `mailboxId`) и «хотя бы один флаг». Автор предлагает шаг
   `apply_input_contract` при регистрации тула. Оцени: это минимальный обходной путь или схемы надо
   чинить иначе (например, вручную править `inputSchema` после генерации — тогда `tools_schema.py`
   перестаёт быть источником истины)?
5. **Реализуемость на Stalwart.** Список живых рисков (из отчёта автора): `Thread/get` + поля
   Thread · `calculateTotal` и его цена · полнотекстовый оператор · `header`/`before`/`after`/
   `hasKeyword`/`notKeyword` · точные строки `role` · формат `downloadUrl`/`uploadUrl` + auth блоб-эндпоинтов ·
   `EmailSubmission/set` + `onSuccessUpdateEmail` (кто переносит в Sent) · `Identity/get`
   (`replyTo`, `isDefault`) · `textBody`/`bodyValues` · набор keywords · наличие `state` в ответе ·
   `$answered` · счётчики `Mailbox`.
   Для каждого: насколько критичен, и **что делать, если не подтвердится** (fallback в схеме/туле).
6. **Дыры в покрытии.** Чего не хватает для сценария владельца (whoami → чтение → поиск → флаги →
   вложения → отправка)? Есть ли тул, который на самом деле лишний?

## Выход

Файл **`reviews/schema-review.md`** (создать каталог `reviews/`), структура:

- **Вердикт** (1–3 строки): принято / принято с правками / не принято.
- Таблица: `пункт (из §1–6) | находка | вердикт | что делать`.
  Вердикт строго один из: `ok` / `fix` / `not worth fixing` / `rejected` / `open`.
  Для `fix` — конкретное действие (что поменять и где), не «улучшить описание».
- **Список правок по приоритету**: блокеры → важно → косметика, с номерами.
- **Риски Stalwart**: таблица `риск | критичность | fallback`.
- **Открытые вопросы к владельцу** (если есть).

## Границы

- **Не переписывать** схемы и не править `tools_schema.py` — это работа автора. Только указать, что
  и где чинить. Если правок много — дать точные формулировки/JSON-фрагменты в отчёте.
- Файлы создавать только внутри репо (`.` = `D:\RocketScience\AI\jmap-mcp-gh`). Отчёт — в `reviews/`.
- **Ничего не коммитить и не пушить.**
- Не предлагать новых тулов без разбора: сначала «нужно ли это владельцу».
- Сеть не нужна. Если нужен внешний факт (RFC 8620/8621, доки Stalwart) — бери из RFC/доков, но
  помечай как непроверенное на живом сервере.
- Не уходить технически ниже штатного инструмента: если инструмент не работает — скажи об этом,
  не добывай токены и не обходи через сырые API-вызовы.
